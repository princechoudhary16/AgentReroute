# Pilot run: gemma4:31b-cloud, 20 tasks (2026-10-20)

First benchmark runs with a real model. Purpose: get real attribution and repair
numbers, and check that the benchmark behaves correctly on real agents.

The pilot ran in three rounds. Each round exposed problems in the benchmark that
were fixed before the next. **The v3 numbers below are the current results**; the
v2 section explains what changed and why.

## Setup (v3)

| Item | Value |
|---|---|
| Model | `gemma4:31b-cloud` via Ollama (open weights, served by Ollama's cloud), temperature 0 |
| Data | τ-bench retail at commit `59a200c`, tasks `retail-000`–`retail-021` minus 012/013 (their gold actions violate τ-bench's own rules) |
| Workflow / operators | workflow v2, operators v2 (both part of the generation settings lock) |

| Outputs | `benchmark/runs/pilot-gemma-v3/` (gitignored): `eval/report.md`, `eval/dashboard.html`, reports |

Reproduce (all model calls are cached, so a rerun reproduces these numbers):


## Generation and agent robustness

- 12 of 20 tasks eligible (60%). The 8 ineligible tasks fail on genuine model errors,
  e.g. reporting 12 T-shirt options where τ-bench expects the 10 *available* ones
  (tasks 002–004) and dropping the `#` from an order id (001).
- 108 injected failures, 101 tolerated, 44 clean controls, 16 natural failures
  (queued for annotation), 0 not activated. All 7 modes are present in the test split.

Robustness = share of injected runs that still succeed (MAS-FIRE robustness score;
ToolMaze success rate):

| Fault | Robustness | Reading |
|---|---:|---|
| `misroute`, `irrelevant_tool`, `drop_context` (once) | 100% | The model notices a wrong route or missing ids and recovers by itself |
| Same three, persistent | 0–9% | A systematic routing or handoff error defeats it |
| `skip_write`, `stuck_processing` | 0% | Never caught |
| `policy_contradiction` no_writes / skip_verification | 9% / 100% | Obeys a false "tools disabled" note; ignores "skip verification" |
| `misread_value` argument / claim, `omit_detail` | 82% / 100% / 73% | Often corrected downstream |
| ToolMaze P1 explicit-transient | 100% | Retries a 503 |
| P2 explicit-permanent | 9% | Cannot route around a dead tool |
| P3 / P4 implicit (stale data), transient / permanent | 18% / 18% | Over-trusts plausible tool output; the explicit − implicit gap for transient faults is 82 points |

## Attribution (test, n = 29)

| System | Step | Step ±1 | Acceptable step | Agent | Mode | Mode macro-F1 |
|---|---:|---:|---:|---:|---:|---:|
| random | 3% | 14% | 3% | 41% | 14% | 0.15 |
| last step | 0% | 31% | 0% | 31% | 3% | 0.01 |
| heuristic | 17% | 41% | 28% | 52% | 31% | 0.34 |
| LLM judge (gemma, all-at-once) | 72% | 93% | 90% | 79% | 72% | 0.67 |

By fault, the judge finds the exact step for every `skip_write`, prompt mutation and
misroute (9/9), 4/5 dropped-context handoffs, 4/6 stale-data faults, 1/3 cycles and
0/2 persistent tool errors (there it names the tool step, i.e. the fault step, not the
agent step after it). It labels most stale-data faults as misinterpretation (mode 5)
rather than tool failure (mode 4): the hardest taxonomy boundary.

## Recovery (test, 29 failed, 39 controls)

| Condition | Recovery | Harm | Cost (× one run) | Planner faults | Specialist faults | Tool faults |
|---|---:|---:|---:|---:|---:|---:|
| no recovery | 0% | 0% | 0 | 0/9 | 0/9 | 0/11 |
| full restart | 7% | 5% | 1.03 | 0/9 | 0/9 | 2/11 |
| retry last step | 7% | 0% | 0.17 | 0/9 | 0/9 | 2/11 |
| fixed rules + heuristic | 28% | 3% | 0.23 | 5/9 | 3/9 | 0/11 |
| generic reflection | 52% | 5% | 0.89 | 9/9 | 1/9 | 5/11 |
| fixed rules + LLM judge | 62% | 3% | 0.28 | 8/9 | 9/9 | 1/11 |
| fixed rules + gold diagnosis (oracle) | 76% | 0% | 0.27 | 9/9 | 9/9 | 4/11 |

Paired McNemar against full restart (n = 29): judge-driven rules p < 0.001 (18 vs 2
episodes recovered by only one side), oracle p < 0.001, generic reflection p < 0.001,
heuristic-driven rules p = 0.11.

### What it shows

1. **Diagnosis-guided rollback works and is cheap.** Rules driven by the LLM judge
   recover 62% of failures at 0.28× the cost of one run; a full restart recovers 7% at
   1.03×. Restarting does not fix a systematic agent mistake; correcting the right
   agent at the right step does.
2. **Better diagnosis means more recovery, monotonically.** The same rules recover
   28% with the heuristic, 62% with the LLM judge and 76% with gold attribution. The
   14-point gap to the oracle is what a better fault attribution system can win.
3. **Generic advice only helps the agent that receives it.** Generic reflection
   (a note to the planner at step 1) fixes every planner mistake but 1 of 9
   specialist mistakes, at nearly full-run cost.
4. **Tool faults are the open problem.** No condition fixes more than 5 of 11: guidance
   cannot change what a tool returns; only transient faults clear on a fresh read.
   Cycles were recovered by nothing.
5. **The judge needs an abstention threshold.** It always proposes a step, so the
   judge-driven policy intervened on 54% of healthy runs (harm 3%). `fixed_rules
   --min-confidence` exists for this; tune it on the calibration split.

All rates have wide intervals at n = 29; the full 115-task run is needed for firm claims.

## What v2 got wrong, and the fixes (v2 → v3)

v2 (same 20 tasks, 65 failures) produced results that looked plausible but were
partly artefacts of the benchmark. Five problems, all fixed and covered by tests in
`benchmark/tests/test_pilot_fixes.py`:

| Problem in v2 | Effect | Fix in v3 |
|---|---|---|
| Agent faults recurred only on an *identical* context | Any earlier change (a new seed, a note at step 1) removed the fault; full restart scored 50%, every non-trivial policy 7/7 on agent faults | Agent faults are systematic: they recur at the same site unless guidance reaches the responsible agent at or before the faulty turn. Full restart drops to 7% |
| Drift and context faults fired once | The model routed around all 44 of them; no mode 2 or 6 failures | `persistent` variants (every later handoff misrouted / stripped); now 0–9% robustness, both modes in the corpus |
| `skip_write` used one canned sentence | Easy to spot | A specific, varied claim built from the skipped call (order id, items, payment method) |
| Fixed 60k token cap | Full restart breached it in 39 of 56 episodes | Cap is 2× the original run's tokens by default; cost reported as a multiple of one run; 0 breaches |
| Robustness metrics (MAS-FIRE RS, ToolMaze TSR/PRR/RC) promised but not computed | Agent robustness was not reported | `scoring/robustness.py`, in `evaluate` and the dashboard |

Earlier, during v1, two workflow faults caused artificial failures (the planner could
not open orders; specialists were told both "confirm with the user" and "already
confirmed") and only 1 of 7 tasks was eligible. Workflow v2 fixed both. A transient
Ollama timeout also stopped a run once; the client now retries timeouts, 429 and 5xx
with backoff.
